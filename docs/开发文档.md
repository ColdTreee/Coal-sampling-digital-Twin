# 基于数字孪生技术的输煤取样系统开发文档

版本：0.1（开发规划稿）  
日期：2026-11-19  
依据：`docs/需求分析.docx`、`docs/0.附件2：辽宁工业大学大学生创新训练计划项目申请书.doc`

## 1. 文档目的

本文把项目申请书中的研究目标和需求分析中的功能设想，转化为适合学生团队分阶段实现的软件工程方案。建议先交付一个可演示、可测试、数据链路闭环的数字孪生原型，不把未经现场验证的能力表述为已具备的工业控制、预测维护或煤质分析系统。

本文的首要建议是采用 Web 单体应用：Vue 3 + TypeScript + Three.js 前端，FastAPI 后端，PostgreSQL 数据库；以模拟器和 MQTT/HTTP 接入构造可重复的演示数据。首期实现设备与流程可视化、批次和样品追溯、规则告警及处置记录。真实 PLC 接入、现场传感器校准、视频识别和生产系统对接均作为有条件的后续工作。

## 2. 依据与需求解读

两份材料的共同目标是：以输煤取样过程为主线，关联来煤批次、采样任务、设备状态、样品流转和异常事件；建立设备、流程、样品的虚拟映射；提供监控、预警、追溯和管理功能。需求稿提出五层架构、边缘与中心协同、断网缓存和补传，以及按角色控制访问。申请书把预期成果定位为软件原型，并安排调研设计、模型与基础开发、功能集成测试、优化总结四个阶段。

以下实施判断作为规划假设，须在项目启动时由团队和指导教师确认：

- 首期面向浏览器和校内演示，不直接接入生产控制网，也不向 PLC 下发控制命令。
- 在没有现场数据、传感器和设备协议资料前，使用模拟数据与人工录入验证业务链路；模拟状态必须在界面标记为“演示数据”。
- “数字孪生”首期指设备/流程状态与事件的可视化映射和历史回放，不宣称高保真物理仿真或预测性维护。
- 首期异常识别采用阈值、状态机和超时规则；机器学习要等到有足量、带标签的现场数据后再评估。
- 采样质量是否符合行业要求需要由业务专家和适用标准验证，软件原型本身不能证明样品具有代表性。

## 3. 目标与范围

### 3.1 首期目标

交付一套可本地部署的演示原型，能够创建或导入来煤批次，生成采样任务，接收设备/传感器模拟数据，实时更新孪生场景，触发可解释的异常告警，记录人工处置，并按批次查看完整事件链和导出追溯报告。

### 3.2 首期功能范围

| 模块 | 首期实现 | 验收表现 |
|---|---|---|
| 用户与权限 | 登录、角色和基础授权；管理员、值班人员、只读查看角色 | 未授权用户不能执行配置、确认或导出等受限操作 |
| 批次与任务 | 批次建档、任务创建、任务状态流转、检索 | 批次可关联多个任务；状态变化留有时间和操作者 |
| 设备台账 | 设备、点位、设备状态和孪生对象映射 | 设备清单与场景中的对象一一对应 |
| 数据接入 | 模拟器优先；REST 和 MQTT 接入适配；输入校验、去重和离线暂存 | 生成、接收、补发测试消息后数据可查询且不重复入账 |
| 数字孪生 | 关键设备和流程的轻量三维/二维视图，状态着色、当前批次、事件回放 | 点击设备可查看状态；回放与批次事件时间线一致 |
| 告警闭环 | 堵煤/卡样/空采/超时/异常振动等规则；确认、备注、关闭 | 可重现规则触发；每条告警有状态、时间和处置记录 |
| 样品追溯 | 批次、采样任务、样品、设备事件、告警之间的关联查询 | 输入批次或样品编号可看到连续事件链及缺失环节提示 |
| 报表导出 | 批次追溯和告警记录 CSV 导出 | 导出数据字段、数量与页面筛选结果一致 |
| 系统审计 | 登录、配置变更、规则修改、告警确认、导出等审计事件 | 管理页面可按时间、用户和操作类型查询 |

### 3.3 明确不纳入首期

- PLC 双向控制、联锁、安全保护或任何会影响生产设备动作的功能。
- 未经验证的煤质预测、采样偏差自动校正、设备寿命预测或机器学习结论。
- 视频 AI 行为识别、视频存储平台建设、门禁系统接入。
- 与采购、地磅、LIMS、ERP、煤场等真实系统的生产级集成。
- 工业级 7×24 可用性承诺、跨厂区部署、商业化多租户及真实工控网络安全认证。

上述能力须分别取得现场数据/设备资料、接口授权、网络安全评审和业务专家确认后，另立需求与验收标准。

## 4. 技术方案比较与推荐

### 方案 A：Web 原型，推荐

- 技术栈：Vue 3 + TypeScript + Vite；Three.js；ECharts；FastAPI + Pydantic + SQLAlchemy；PostgreSQL；Mosquitto MQTT（演示环境可选）；Docker Compose；pytest 与 Playwright。
- 适用理由：浏览器即可展示，Python 便于编写数据模拟、规则分析和后续算法试验；Three.js 支持在 Web 场景中构建设备/流程视图；PostgreSQL 统一保存业务记录和时序采样点，减少早期运维组件。
- 开发难度/维护成本：中低；需要团队具备或补齐 TypeScript、Python、SQL 和基础三维场景开发能力。
- 目标地区可用性：技术为开源 Web 组件，可在校内服务器或本地演示机运行；外部云服务不是首期前提。
- 自行维护：应用与数据库部署、账号权限、备份、依赖更新；不需要先搭建 Kubernetes 或独立时序数据库。
- 主要风险：团队如果没有 Python 经验，后端学习成本会上升；Three.js 建模和性能调优需要限制场景复杂度。

### 方案 B：Java 企业后端

- 技术栈：Vue 3 + TypeScript + Three.js；Spring Boot；PostgreSQL；MQTT Broker；Docker Compose。
- 适用理由：适合已有 Java/Spring 课程基础、希望练习企业后端分层与长期扩展的团队。
- 开发难度/维护成本：中；工程结构规范但样板和配置相对更多，规则算法试验通常需要额外的数据分析服务或 Java 实现。
- 目标地区可用性：可本地或校内部署，不依赖特定云平台。
- 自行维护：JVM 服务、数据库、消息代理、权限与备份。
- 主要风险：如果成员缺少 Spring Boot 经验，首期完成成本可能高于方案 A；跨语言增加部署复杂度。

### 方案 C：Unity 三维客户端

- 技术栈：Unity；C# 服务端（ASP.NET Core）或独立 API；PostgreSQL；MQTT。
- 适用理由：适合把沉浸式三维、设备动画和展厅演示作为首要成果的团队。
- 开发难度/维护成本：中高；客户端部署、账号管理、数据接口、版本分发和 Web 管理端会形成两套应用面。
- 目标地区可用性：可离线演示，但客户端安装和硬件要求需单独管理。
- 自行维护：Unity 项目、客户端打包、服务端、数据库和协议集成。
- 主要风险：容易把时间投入视觉效果，压缩批次关联、数据质量和追溯闭环的实现时间。

**推荐方案 A。** 决定性理由是它能以较低的基础设施和团队协作成本同时覆盖 Web 监控、事件数据处理和三维孪生展示。若团队已有明显更强的 Java 或 Unity 实践经验，应优先服从实际技能而不是机械坚持推荐方案。

## 5. 总体架构

首期采用模块化单体，按逻辑职责分层，先避免微服务。物理设备层只作为建模对象；接入层通过模拟器、HTTP 或 MQTT 产生数据；后端负责校验、业务关联、规则判断、持久化和查询；前端分为业务页面与孪生视图。

```text
演示数据模拟器 / 人工录入 / 未来的只读设备网关
                      |
              HTTP REST / MQTT
                      |
  FastAPI 接入与业务服务（校验、关联、告警、审计）
           |                      |
     PostgreSQL            WebSocket 推送
           |                      |
 Vue 业务页面 + Three.js 孪生视图 + ECharts 趋势图
```

建议的后端模块边界：

- `auth`：身份认证、角色和授权依赖。
- `master_data`：设备、传感器点位、规则和编码字典。
- `batches`：批次、采样任务和样品业务状态。
- `ingestion`：REST/MQTT 输入适配、数据校验、去重和缓存/补传接口。
- `events`：统一事件模型、时间线和关联查询。
- `alarms`：规则评估、告警状态机和处置记录。
- `twin`：孪生当前状态聚合、历史回放查询。
- `reports`：追溯报告和 CSV 导出。
- `audit`：关键操作审计。

数据流：模拟器或接入适配器发出带设备编号、采集时间和事件类型的数据；服务端校验编码和时间，按幂等键去重；将原始测点/业务事件持久化并关联当前任务；规则模块生成或更新告警；通过 WebSocket 通知前端，前端查询 REST API 获取完整详情。断网补传的真实边缘实现不作为首期验收项，但数据模型应保留 `source_id`、`event_time`、`received_at` 和 `idempotency_key` 字段以支持后续扩展。

## 6. 关键数据设计

关系型数据库首期可包含以下实体。主键统一使用 UUID；业务编号（如批次号、样品号）另设唯一约束；所有时间采用带时区时间戳，数据库和服务统一使用 UTC 存储，页面按本地时区展示。

| 实体 | 主要字段 | 说明 |
|---|---|---|
| `users` / `roles` | 用户名、密码哈希、角色、启用状态 | 不保存明文密码；权限采用角色控制 |
| `devices` | 设备编号、名称、类型、位置、孪生对象键、状态 | 台账与场景对象的映射来源 |
| `sensor_points` | 点位编号、设备编号、指标、单位、量程、阈值 | 传感器配置和规则参数引用 |
| `coal_batches` | 批次编号、来源、运输方式、到达时间、状态 | 业务追溯主线之一 |
| `sampling_tasks` | 任务编号、批次编号、计划/实际时间、状态、策略版本 | 记录任务执行生命周期 |
| `samples` | 样品编号、任务编号、样品类型、当前位置、封存状态 | 样品流转主记录 |
| `telemetry_points` | 设备/点位编号、采集时间、接收时间、数值、质量标志、来源 | 传感器/模拟器测点数据 |
| `events` | 事件类型、对象类型/编号、批次/任务/样品编号、时间、负载、幂等键 | 统一记录状态变化和人工操作关联 |
| `alarm_rules` | 规则编号、条件、持续时间、级别、启用状态、版本 | 首期规则可配置阈值和超时 |
| `alarms` / `alarm_actions` | 告警来源、级别、状态、触发/确认/关闭时间、处置备注 | 支持告警闭环和追责 |
| `audit_logs` | 操作者、动作、目标、时间、结果、必要的变更摘要 | 不记录密码、令牌等秘密信息 |

关键一致性规则：批次编号、任务编号、样品编号、设备编号必须校验存在；一个采样任务必须归属一个批次；一个样品必须能追溯到其来源任务；关键状态变化必须形成事件；同一幂等键不得重复入账；删除业务数据默认采用停用/作废并留审计记录，而不是物理删除。

## 7. 接口约定

业务查询和管理使用版本化 JSON API，例如 `/api/v1`。写请求需校验身份和权限；错误返回统一包含 `code`、`message`、`request_id`。列表接口使用分页和明确的筛选条件。实时更新采用 WebSocket 推送轻量事件通知，前端收到通知后再调用 REST 获取详情，避免把实时连接当作历史数据存储。

建议首期 API：

- `POST /api/v1/batches`：创建批次。
- `GET /api/v1/batches/{batch_id}/trace`：获取批次任务、样品、事件、告警组成的追溯链。
- `POST /api/v1/sampling-tasks`：创建采样任务。
- `POST /api/v1/ingestion/telemetry`：接收一条或一批测点数据。
- `GET /api/v1/twin/state`：查询孪生视图的当前聚合状态。
- `GET /api/v1/alarms`、`POST /api/v1/alarms/{alarm_id}/actions`：查询和处置告警。
- `GET /api/v1/reports/trace.csv`：按授权条件导出追溯数据。

测点消息至少包含 `message_id`、`device_id`、`point_id`、`event_time`、`value`、`unit`、`quality` 和 `source`。事件统一有 `event_id`、`event_type`、`occurred_at`、`device_id`、可选的 `batch_id`/`task_id`/`sample_id`、`payload` 和 `idempotency_key`。MQTT Topic 可采用 `coal-sampling/{site}/{device}/telemetry` 和 `coal-sampling/{site}/{device}/event`；部署前必须确认认证、TLS、ACL 和网络边界，不能把公开匿名 Broker 接入现场。

## 8. 规则与孪生建模

### 8.1 首期规则

- 超阈值：振动、电流或温湿度超过经确认的演示阈值并持续指定时长。
- 流程超时：样品或任务在某节点停留超过配置时长。
- 动作缺失：任务处于执行状态但在观察窗口内没有预期采样事件。
- 状态不一致：样品位置、设备状态和流程节点不能组成合法转换。
- 数据质量异常：设备/点位未知、时间超前/过旧、数值越量程、同一消息重复。

所有告警需展示触发条件、关联对象、首次触发时间和建议核查动作。项目原型中的建议属于规则提示，不是自动控制命令，也不应被表述为已验证维修结论。

### 8.2 轻量孪生

从设备清单中选取采样头、输送/给料、破碎、缩分、集样等关键对象，用简化几何体或可授权使用的 glTF 模型组成场景；通过稳定的 `twin_object_key` 映射设备编号。状态颜色、当前流程节点、批次号、报警标记和样品位置都由服务端状态驱动。将状态渲染、业务状态计算和三维资源加载分离，确保没有 WebGL 时仍可通过列表和流程图完成核心业务演示。

## 9. 非功能要求与安全

建议将需求稿的性能指标作为原型目标，而不是生产 SLA。使用固定数据集和测试环境记录测试方法、数据规模和结果。

| 指标 | 原型验收目标 | 说明 |
|---|---|---|
| 主监控/常用查询 | 95% 请求响应小于 3 秒 | 约定测试数据规模和本地/服务器环境 |
| 批次追溯 | 结果小于 10 秒 | 使用含完整事件链的测试批次 |
| 告警展示 | 规则触发后 5 秒内出现在页面 | 在单机演示环境测量端到端延迟 |
| 关键事件完整性 | 测试用例中无遗漏、无重复关联 | 不将测试结果外推为现场数据准确率 |
| 可恢复性 | 重启后业务记录保留；模拟重复消息不重复入账 | 备份/恢复过程需要写入测试记录 |

安全基线：全程只读接触现场信号；应用与 PLC 控制网隔离；开发环境不得含真实生产凭证；密码使用经过验证的哈希方案存储；管理接口进行服务器端授权检查；MQTT 禁用匿名访问；敏感配置由环境变量或受控配置文件提供且不提交到 Git；参数修改、告警处置和导出写审计日志；数据库定期备份并测试恢复。未经现场网络安全负责人审核，不部署到生产网络。

## 10. 测试与验收

- 单元测试：事件校验、幂等去重、任务/样品状态转换、规则边界条件、权限判断。
- 集成测试：API 与 PostgreSQL 的创建、查询、事务回滚、批量数据接收、追溯结果关联。
- 端到端测试：登录、创建批次、运行模拟器、触发告警、人工确认、查询追溯、导出 CSV。
- 可视化验证：设备状态颜色与后端状态一致；页面断开实时连接后可重新连接并通过 REST 补齐当前状态；无三维支持时核心页面仍可操作。
- 异常测试：非法设备/点位、重复消息、乱序时间、数据库短时不可用、MQTT 断开与恢复、无权限操作、空批次/缺环节追溯。
- 文档验收：部署说明、配置清单、数据字典、API 文档、测试报告、已知限制和演示脚本齐备。

演示验收至少准备三类脚本：正常完成一个批次；触发一条设备阈值告警并闭环处置；模拟样品流转超时或事件缺失并在追溯页定位问题。每个脚本都要可重置、可重复运行，且显式说明哪些数据为模拟数据。

## 11. 迭代计划

以下按 16 周规划，实际周次应根据学校项目周期和团队可投入时间调整。

| 周次 | 阶段 | 交付物 / 出口条件 |
|---|---|---|
| 1-2 | 需求确认与原型 | 用例、业务流程、术语表、系统边界、页面草图、风险与数据来源清单；导师确认首期范围 |
| 3-4 | 架构与基础框架 | 数据模型、API 草案、前后端骨架、数据库迁移、模拟数据协议；完成一条端到端健康路径 |
| 5-7 | 核心业务 | 批次、任务、设备台账、样品、事件和追溯查询；核心关联约束有自动化测试 |
| 8-10 | 实时采集与孪生 | 模拟器、HTTP/MQTT 接入、状态聚合、Three.js 场景、趋势图和事件回放 |
| 11-12 | 告警与管理 | 规则、告警确认、审计、权限、CSV 导出；三类告警演示通过 |
| 13-14 | 集成与质量 | 异常测试、端到端测试、性能记录、修复高优先级缺陷 |
| 15-16 | 部署与验收 | 一键启动或清晰部署手册、演示数据、用户说明、技术文档、验收报告和结题材料 |

每个迭代结束应有可运行版本、已知问题清单和演示记录。关键功能按优先级 P0（批次/事件关联、追溯、告警）→ P1（孪生展示、权限、报表）→ P2（真实硬件、视频、算法扩展）推进。

## 12. 团队分工与协作

角色可由成员兼任，但每个模块需有一位明确负责人和至少一位代码审查者：

- 项目/需求负责人：需求澄清、业务流程、标准和验收协调。
- 前端负责人：Vue 页面、状态管理、图表和业务交互。
- 孪生负责人：设备清单、模型资源、Three.js 场景和状态映射。
- 后端/数据负责人：API、数据库、事件模型、规则与追溯。
- 测试/部署负责人：自动化测试、模拟器、Docker Compose、部署和演示材料。

代码采用 Git 分支和 Pull Request/Merge Request 协作；每次提交应对应需求或缺陷编号；接口和数据结构先评审再并行开发；禁止多人直接改同一核心模块而不合并审查。密钥、个人信息和未经许可的现场数据不得提交仓库。

## 13. 仓库与交付建议

建议的项目代码目录：

```text
frontend/                 Vue 页面与孪生视图
backend/app/              FastAPI 模块
backend/migrations/       数据库迁移
simulator/                可复现的演示数据生成器
infra/                    Docker Compose 与本地部署配置
tests/                    API、集成和端到端测试
docs/                     需求、架构、接口、数据字典、测试与部署文档
```

首期不建议引入 Kubernetes、微服务拆分、独立 Redis、独立时序数据库或自研规则引擎。只有在数据量、并发、隔离或运维需求被实测证明后再增加组件。时序数据可先放在 PostgreSQL 的测点表中，并按时间和设备建立合适索引；后续再根据保留周期与吞吐测试决定是否采用专用时序数据库。

## 14. 项目风险与待确认事项

1. **现场条件未知**：目前材料没有确认可用 PLC 型号、通信协议、真实数据授权或现场网络窗口。先做模拟数据适配；取得设备清单和只读测试条件后再编写真实驱动。
2. **数字孪生定义过宽**：需要导师确认验收重点是设备状态可视化、流程回放，还是高精度三维建模。首期建议前两项。
3. **样本与阈值缺失**：异常阈值和样品超时规则须经业务人员确认；默认演示阈值不可直接用于生产。
4. **标准适用性需核验**：需求稿列有 GB/T 19494.1-2023、GB/T 19494.2-2023、GB/T 474-2008、GB/T 30730-2014、GB/T 30731-2014、GB/T 43219-2023。正式设计和验收前应由指导教师/企业业务人员核对标准现行状态、适用范围和具体条款；本软件方案不替代标准审查。
5. **团队配置待核对**：申请书填表说明写明项目团队至少 5 人（含主持人），而当前项目成员表可见人数少于该要求。应核对是否为未完成版本，并在提交前补齐成员与独立分工。
6. **成果与经费口径需统一**：申请书预期成果提到发明专利和软件著作权，但预算表对相关支出写法不完全一致；应由项目负责人核实知识产权目标与预算表口径。
7. **性能目标需可复现**：99% 完整率、5 秒告警延迟和 7×24 运行不能只写在文档中。首期按固定数据规模、测试步骤、环境和观测结果报告；未做长时间稳定性测试前不宣称已达到生产级稳定性。

项目启动评审需确定：首期演示地点和使用角色；可用的设备/流程图纸和素材授权；演示电脑/服务器操作系统；团队各成员已掌握的语言与框架；学校项目的结题日期与验收形式；是否存在真实传感器/PLC及只读接入审批。

## 15. 技术落地顺序

1. 先冻结 MVP 用例、状态机、编码规范和事件字段，做一份可手工核验的追溯样例。
2. 建立 PostgreSQL 数据模型、迁移脚本和 FastAPI 接口，实现批次—任务—样品—事件查询闭环。
3. 用模拟器持续生成正常、告警、断连、重复和乱序数据，先验证事件处理和规则的可复现性。
4. 开发 Vue 管理页面与 Three.js 轻量场景，以同一设备编号和事件时间线驱动列表、孪生状态和回放。
5. 补上权限、审计、导出、异常测试与一键演示部署；稳定后再评估真实设备只读接入和算法增强。
